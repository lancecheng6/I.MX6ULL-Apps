# Day 10 — Pi Agent（類似 OpenClaw 的 Agent）部署於嵌入式 i.MX6ULL：Node.js、pi 安裝（2026-08-05）

**目標：** 將開源 **Pi coding agent**（`earendil-works/pi`）帶上 32-bit ARM 的 i.MX6ULL 開發板，**終極目標是讓 AI 能自主控制嵌入式硬體並做決策**——讀取感測器、驅動 GPIO、與 UART/RS-485 周邊通訊，並根據自己的推理實際操作開發板。

**本日（第一座里程碑）：** 建立部署基礎與「人 ↔ AI ↔ 硬體」的通道——安裝 Node.js 執行環境、安裝 pi 的 npm 套件、設定可用的 LLM provider，並包裝成 Qt5 SystemUI 的 App（`PiAgent`），以 headless RPC 模式與 pi 通訊——過程中針對「聊天列表串流自動捲動」進行深度除錯，這是今天最硬的一場仗。

> **為什麼要在嵌入式板子上放 AI agent：** pi 是 *agent*，不是純聊天機器人——它用 LLM 推理，然後透過工具（`bash`、`read`、`write`、`grep`、`find`、`ls`，以及可擴充的 extensions/skills）**實際行動**。這正是「自主控制硬體」需要的：AI 可以檢查系統（`/sys`、GPIO、串列裝置）、決定要做什麼，然後真的去驅動硬體（設定 GPIO、送 UART 指令、切換繼電器）。今天的工作讓 agent 在板子上有了家、也有了指揮它的使用者介面；硬體控制工具（例如 `gpio_set`、`uart_send`、`sensor_read`）就是在這個基礎上的自然下一步。

---

## 1. 平台評估與規劃

### 1.1 pi 是什麼

`earendil-works/pi` 是以 TypeScript/Bun 寫成的可擴充 coding agent（互動 TUI + agent 迴圈 + 統一 LLM API）。它**不做本地推論**——連線到各家遠端 LLM API（Anthropic、OpenAI、DeepSeek、OpenCode Zen/Go……）。

### 1.2 為什麼走 npm 路線（而不是官方 binary）

- 官方 standalone binary（Bun 編譯）只提供 `linux-x64 / linux-arm64 / darwin / windows-*`——**沒有 32-bit ARM**。
- npm 套件 `@earendil-works/pi-coding-agent` 要求 `node >= 22.19.0`，而 **Node.js 官方有提供 `linux-armv7l` 預編譯 tarball** → 零編譯路徑：
  `Node 22 (armv7l) → npm install pi → pi --mode rpc（headless）`。

### 1.3 硬體現實

i.MX6ULL：單核 Cortex-A7（約 396 MHz）、512MB RAM、無 GPU。pi 必須以 headless（RPC 模式）跑在 Qt 聊天 App 內；Node 冷啟動約 20–40 秒；量測 pi 運行記憶體約 **34 MB**（print 模式）。

## 2. Node.js 安裝（armv7l）

1. 在主機（Hermes/WSL）下載 `node-v22.19.0-linux-armv7l.tar.xz`（26 MB）再 scp 到板子——**板子直接下載會當機**（單核 + HTTPS 負載把系統拖垮）。
2. **busybox tar 不支援 `-J`（xz）** → `xz -dc node.tar.xz > node.tar` 再 `tar -xf -C /opt/node --strip-components=1`（板子有 `/usr/bin/xz`）。
3. 在 `/etc/profile` 加 `export PATH=/opt/node/bin:$PATH`。
4. **`CERT_NOT_YET_VALID`**：npm 失敗，因為板子時間停在 1970-01-01（無 RTC）→ TLS 憑證「尚未生效」。
   - 立即解：`date -s "2026-08-06 ..."`。
   - **永久解：`S55ntp`**——開機腳本從 HTTP `Date:` 標頭校時（`wget -S http://neverssl.com/` → 解析 RFC822 → `date -s`），順序在 `S50wifi` 之後、`S99systemui` 之前。

## 3. Pi Agent 安裝

```sh
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
# /opt/node/bin/pi → symlink → dist/cli.js（#!/usr/bin/env node）
```

### 3.1 Provider 曲折（OpenCode Zen vs Go）

- 內建 `opencode` / `opencode-go` provider 打到 **Go 訂閱** endpoint，回 `CreditsError: Insufficient balance`。
- 板子既有的 DeepSeek App 用的是 **Zen** endpoint `https://opencode.ai/zen/go/v1/chat/completions`、model `deepseek-v4-flash`——手上的 API key 走這條能用。
- **解：在 `~/.pi/agent/models.json` 自訂 provider**：

```json
{
  "providers": {
    "opencode-zen": {
      "baseUrl": "https://opencode.ai/zen/go/v1",
      "api": "openai-completions",
      "apiKey": "sk-...",
      "models": [ { "id": "deepseek-v4-flash", "name": "DeepSeek V4 Flash (Zen)" } ]
    }
  }
}
```

- 驗證：`pi -p "Reply with exactly: RPC OK" --provider opencode-zen --model deepseek-v4-flash` → `OK`。

## 4. RPC 通道驗證

`pi --mode rpc` 以 LF 分隔 JSONL 在 stdin/stdout 收發。送
`{"id":"r1","type":"prompt","message":"..."}` 會得到 `response` + `agent_start`/`turn_start`/`message_*`/`message_update`（text_start/delta/end）/`turn_end`/`agent_end`/`agent_settled`。**stdin 必須保持開啟**（EOF 會讓 pi 退出）。

## 5. PiAgent Qt App

```
main.qml（聊天 UI）── QML context ── PiAgentclient（QProcess）
                                      └─ node cli.js --mode rpc --provider opencode-zen --model deepseek-v4-flash
                                         stdin/stdout JSONL
```

- `PiAgentclient`：QProcess + JSONL 解析；把 `text_delta` 累積進回合緩衝；emit `partialUpdate(text)`（節流）與 `replyReceived(text)`（`agent_end` 時）。
- QML：單一 assistant 氣泡就地更新；虛擬鍵盤用 `InputPanel`（`QT_IM_MODULE=qtvirtualkeyboard`）；懸浮球（回桌面）用 `Client` 元件（`com.alientek.qmlcomponents`，需 `client/client.pri` + Qt Remote Objects）。

這個架構刻意就是**自主硬體操作的「控制通道」**：agent 本來就有 `bash`（可以直接 `echo 1 > /sys/class/...`、`devmem`、`gpioset`、`stty`/`echo` 到串列埠等），而 pi 的 extension/skill 機制可以註冊專用硬體工具（`gpio_set`、`uart_send`、`sensor_read`、`relay_toggle`），讓 AI 自己感測、決策、並實際驅動嵌入式系統。

## 6. 問題與解法（表格）

| 問題 | 根因 | 解法 |
|---------|-----------|-----|
| 板子直接下載 Node 當機 | 單核 + HTTPS 超載 | 主機下載、scp 轉傳 |
| `tar: invalid option -- 'J'` | busybox tar 無 xz | `xz -dc` 再 `tar -xf` |
| npm `CERT_NOT_YET_VALID` | 板子時間 1970（無 RTC）| `date -s` + **S55ntp** 開機校時 |
| QProcess 的子程序找不到「node」| 進程標題是 **`pi`** 不是 `node` | grep 用 `pi`；直接 `/opt/node/bin/node .../dist/cli.js` |
| 重開機後 `Error: Unknown provider "opencode-zen"` | systemui 繼承 `HOME=/` → pi 讀 `/.pi/...` | QProcess 環境**強制 `HOME=/root`** |
| `AppMainBody is not a type` | `Client.qml` 需要 `AppMainBody.qml` | 從 DeepSeek App 複製 |
| 沒有虛擬鍵盤 | 缺 `InputPanel` 元件 | 加 `InputPanel` + 輸入列重新錨定 |
| 沒有懸浮球／無法回桌面 | 缺 `Client` + remoteobjects | 加 `Client { programmerName }` + `client.pri` |
| 一個問題多個氣泡、不知結束 | 每個 `text_end` 都發 | 收集整個回合；`agent_end` 才發一次；`working/ready` 狀態；working 期間鎖 Send |
| `pi exited with code 1` | （見 HOME= 那行）| 強制 `HOME=/root` |

## 7. 🔴 聊天列表捲動除錯（大重點）

一整天的硬仗是串流期間聊天 `ListView` 的自動捲動。

### 7.1 問題 A — ScrollBar 跳動／畫面跳動（長回答後）

**現象：** 長回答結束後往上拖，ScrollBar 長度會變、畫面會跳。

**原因：** 動態高度 delegate（`textContent.implicitHeight + 32`）；ListView 會銷毀/重建畫面外的 delegate → `contentHeight` 重算 → ScrollBar 比例變化 → 跳動。

**解：** `cacheBuffer: chatList.height * 3`（保留約 3 個畫面的 delegate；用動態值在 512MB 板子上控制 RAM）。

### 7.2 問題 B — 第二個問題不會自動捲

**現象：** 往上滾看完第一題答案後，送第二題不會捲到新內容。

**原因：** 自動捲動只有在 `isNearBottom()` 成立時才觸發。

**解：** 在 `send()` 內強制 `Qt.callLater(chatList.positionViewAtEnd)`——送出問題代表「我要看新內容」。

### 7.3 問題 C — 最後一行被輸入框擋住

**解：** `footer: Item { height: 24 }` 留白 + `anchors.bottomMargin: 24`，讓 `positionViewAtEnd` 在最後氣泡下方留出空間。

### 7.4 問題 D — 串流跟隨中途停住（真正的魔王）

**現象：** 遇到超長、大量工具的答案（「Can you control this embedded system?」→ **967 個 text_delta、多輪工具**）時，畫面跟隨一陣子後**停住**——狀態仍「Pi agent working...」——直到 ready 後使用者往下拖才發現下面還有內容。

**診斷（錄下完整 RPC 串流）：**
- `agent_end`（第 5967 行）在最後 `text_delta`（第 5962 行）**之後** → ready 信號本身沒有早到。
- 「ready 太早」的**錯覺**其實是 **UI 卡頓**：每個 `text_delta` → `partialUpdate` → `chatModel.set()` → 396MHz 單核上每次 Text 重新 layout → 事件處理落後，ready 出現時畫面文字還沒追上。
- **捲動停住的根因**：節流更新讓 `contentHeight` 一次長高 >50px；`isNearBottom()`（50px 容差）變 false → 不再 `positionViewAtEnd` → `contentY` 凍結 → **`isNearBottom()` 永遠 false（死鎖）**。

**修復（兩層）：**
1. **節流 UI 更新**（C++）：累積 delta，用 100ms single-shot QTimer 沖刷 → 967 次 set 變 ~10 次 → UI 保持反應（也治好「ready 太早」的錯覺）。
2. **用 `userScrolling` 旗標取代 `isNearBottom()` 容差**：
   ```qml
   property bool userScrolling: false
   onDragStarted:  userScrolling = true
   onDragEnded:    userScrolling = false
   onFlickStarted: userScrolling = true
   onFlickEnded:   userScrolling = false

   onContentHeightChanged: {
       if (waiting && !userScrolling)
           Qt.callLater(chatList.positionViewAtEnd)
   }
   onCountChanged: {
       if (!userScrolling)
           Qt.callLater(chatList.positionViewAtEnd)
   }
   ```
   - 串流中：除非使用者在拖/甩，否則一律釘在底部。
   - **重要：不要用 ListView 的 `moving`**（程式化捲動也會讓它變 true → 又死鎖）；`drag/flick` 訊號只有使用者會觸發。

## 9. 重點總結

1. **目標是「自主控制硬體」而不是聊天**：選 headless RPC + 可擴充工具，正是為了讓 agent 未來能直接驅動 GPIO、UART、感測器並依自己的決策行動。
2. **32-bit ARM + 現代 Node 工具鏈可行**：官方 `linux-armv7l` Node 預編譯存在，完全不用自己編譯。
3. **TLS 一定要校時**：任何 HTTPS 客戶端都會遇到 `CERT_NOT_YET_VALID`；用開機校時（HTTP `Date:` 標頭）持久解決。
4. **pi 的進程名是 `pi` 不是 `node`**——用 `ps | grep pi` 驗證。
5. **HOME 很重要**：從 SystemUI 啟動的 QProcess 繼承 `HOME=/`；一律強制 `HOME=/root`。
6. **Provider endpoint 有差**：OpenCode Zen（`/zen/go/v1`）與 Go 訂閱 endpoint 不同——用 `models.json` 自訂 provider 鎖定正確的。
7. **RPC 模式 stdin 要保持開啟**（EOF 會殺掉 pi）。
8. **串流 UI 必須節流**：在慢速核心上每個 delta 都 `set()` 會卡死 UI，而且看起來像「ready 太早」。
9. **`isNearBottom()` 容差在節流長高下會死鎖**——改用使用者互動旗標（`drag/flick` 訊號），絕不要用 `moving`。
10. **`cacheBuffer`（動態 `height*3`）** 修好動態高度 delegate 的 ScrollBar 跳動，且不會 OOM。
11. **`footer` 留白** 保證最後一行不會被輸入框擋住。
