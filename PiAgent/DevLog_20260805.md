# Day 10 — Pi Agent on Embedded i.MX6ULL: Node.js, pi Deployment & Qt SystemUI Chat App (2026-08-05)

**Objective:** Bring the open-source **Pi coding agent** (`earendil-works/pi`)
onto the 32-bit ARM i.MX6ULL board, with the **ultimate goal of letting the AI
autonomously control the embedded hardware and make decisions** — reading
sensors, driving GPIOs, talking to UART/RS-485 peripherals, and acting on the
board based on its own reasoning.

**This day (first milestone):** build the deployment foundation and the
"human ↔ AI ↔ hardware" channel — install the Node.js runtime, install the pi
npm package, configure a working LLM provider, and wrap it in a Qt5 SystemUI
app (`PiAgent`) that talks to pi in headless RPC mode — including deep
debugging of the chat-list streaming auto-scroll, the biggest battle of the
day.

> **Why an AI agent on an embedded board:** pi is an *agent*, not just a chat
> bot — it reasons with an LLM and then *acts* through tools (`bash`, `read`,
> `write`, `grep`, `find`, `ls`, plus custom extensions/skills). That is exactly
> what "autonomous hardware control" needs: the AI can inspect the system
> (`/sys`, GPIO, serial devices), decide what to do, and then really drive the
> hardware (set a GPIO, send a UART command, toggle a relay). This day's work
> gives the agent a home on the board and a user interface to command it;
> hardware-control tools (e.g. `gpio_set`, `uart_send`, `sensor_read`) are the
> natural next step on top of this foundation.

## 1. Platform Assessment & Planning

### 1.1 What pi is

`earendil-works/pi` is a TypeScript/Bun-based, extensible coding agent
(interactive TUI + agent loop + unified LLM API). It does **not** do local
inference — it calls remote LLM APIs (Anthropic, OpenAI, DeepSeek, OpenCode
Zen/Go, …).

### 1.2 Why the npm path (and not the official binary)

- Official standalone binaries (Bun-compiled) only ship for
  `linux-x64 / linux-arm64 / darwin / windows-*` — **no 32-bit ARM**.
- The npm package `@earendil-works/pi-coding-agent` requires
  `node >= 22.19.0`, and **Node.js provides official `linux-armv7l` prebuilt
  tarballs** → zero-compilation path:
  `Node 22 (armv7l) → npm install pi → pi --mode rpc (headless)`.

### 1.3 Hardware reality

i.MX6ULL: single-core Cortex-A7 (~396 MHz), 512 MB RAM, no GPU. pi must run
headless (RPC mode) inside a Qt chat app; Node cold start takes 20–40 s;
memory footprint measured at ~34 MB for a running pi (print mode).

## 2. Node.js Installation (armv7l)

1. Downloaded `node-v22.19.0-linux-armv7l.tar.xz` (26 MB) on the host
   (Hermes/WSL) and scp'd it to the board — **the board itself crashed when
   downloading directly** (single-core + HTTPS choked the system).
2. **busybox tar does not support `-J` (xz)** → `xz -dc node.tar.xz > node.tar`
   then `tar -xf -C /opt/node --strip-components=1` (the board has `/usr/bin/xz`).
3. Added `export PATH=/opt/node/bin:$PATH` to `/etc/profile`.
4. **`CERT_NOT_YET_VALID`**: npm failed because the board clock was at
   1970-01-01 (no RTC) → TLS certificates "not yet valid".
   - Immediate fix: `date -s "2026-08-06 ..."`.
   - **Permanent fix: `S55ntp`** — a boot script that syncs the clock from an
     HTTP `Date:` header (`wget -S http://neverssl.com/` → parse RFC822 →
     `date -s`), ordered after `S50wifi` and before `S99systemui`.

## 3. Pi Agent Installation

```sh
npm install -g --ignore-scripts @earendil-works/pi-coding-agent
# /opt/node/bin/pi → symlink → dist/cli.js (#!/usr/bin/env node)
```

### 3.1 Provider saga (OpenCode Zen vs Go)

- Built-in `opencode` / `opencode-go` providers hit the **Go-subscription**
  endpoint and returned `CreditsError: Insufficient balance`.
- The board's existing DeepSeek app uses the **Zen** endpoint
  `https://opencode.ai/zen/go/v1/chat/completions` with model
  `deepseek-v4-flash` — which works with the API key at hand.
- **Fix: custom provider** in `~/.pi/agent/models.json`:

```json
{
  "providers": {
    "opencode-zen": {
      "baseUrl": "https://opencode.ai/zen/go/v1",
      "api": "openai-completions",
      "apiKey": "sk-...",
      "models": [ { "id": "deepseek-v4-flash", "name": "DeepSeek V4 Flash (Zen)" } ]
    }
  }
}
```

- Verified: `pi -p "Reply with exactly: RPC OK" --provider opencode-zen --model deepseek-v4-flash` → `OK`.

## 4. RPC Channel Validation

`pi --mode rpc` speaks LF-delimited JSONL over stdin/stdout. A prompt
`{"id":"r1","type":"prompt","message":"..."}` produces `response` +
`agent_start`/`turn_start`/`message_*`/`message_update` (text_start/delta/end)/
`turn_end`/`agent_end`/`agent_settled`. **stdin must stay open** (EOF exits pi).

## 5. PiAgent Qt App

```
main.qml (chat UI) ── QML context ── PiAgentclient (QProcess)
                                          └─ node cli.js --mode rpc --provider opencode-zen --model deepseek-v4-flash
                                             stdin/stdout JSONL
```

- `PiAgentclient`: QProcess + JSONL parser; accumulates `text_delta` into a
  turn buffer; emits `partialUpdate(text)` (throttled) and
  `replyReceived(text)` on `agent_end`.
- QML: single assistant bubble updated in place; virtual keyboard via
  `InputPanel` (`QT_IM_MODULE=qtvirtualkeyboard`); floating ball (back to
  desktop) via the `Client` component (`com.alientek.qmlcomponents`, needs
  `client/client.pri` + Qt Remote Objects).

This architecture is deliberately the **control channel for autonomous
hardware operation**: the agent already has `bash` (it can run
`echo 1 > /sys/class/...`, `devmem`, `gpioset`, `stty`/`echo` to a serial
port, etc.) and pi's extension/skill mechanism can register purpose-built
hardware tools (`gpio_set`, `uart_send`, `sensor_read`, `relay_toggle`) so the
AI can sense, decide, and actuate the embedded system by itself.

## 6. Problems & Solutions (table)

| Problem | Root cause | Fix |
|---------|-----------|-----|
| Board crashed downloading Node directly | single-core + HTTPS overload | download on host, scp to board |
| `tar: invalid option -- 'J'` | busybox tar lacks xz | `xz -dc` then `tar -xf` |
| npm `CERT_NOT_YET_VALID` | board clock at 1970 (no RTC) | `date -s` + **S55ntp** boot time-sync |
| QProcess spawned process not found as "node" | process title is **`pi`**, not `node` | grep for `pi`; use `/opt/node/bin/node .../dist/cli.js` directly |
| `Error: Unknown provider "opencode-zen"` after reboot | systemui inherits `HOME=/` → pi reads `/.pi/...` | force `HOME=/root` in QProcess env |
| `AppMainBody is not a type` | `Client.qml` needs `AppMainBody.qml` | copy from DeepSeek app |
| No virtual keyboard | missing `InputPanel` element | add `InputPanel` + re-anchor input bar |
| No floating ball / can't exit | missing `Client` + remoteobjects | add `Client { programmerName }` + `client.pri` |
| One question → many bubbles, no end signal | emitted on every `text_end` | collect whole turn; emit once on `agent_end`; `working/ready` status; Send locked while working |
| `pi exited with code 1` | (see HOME= row) | force `HOME=/root` |

## 7. 🔴 Chat-List Scroll Debugging (the big one)

The day-long battle was the chat `ListView` auto-scroll during streaming.

### 7.1 Problem A — ScrollBar jumping / view jumping (after long answer)

**Symptom:** after a long reply, dragging up caused the ScrollBar to change
length and the view to jump.

**Cause:** dynamic-height delegate (`textContent.implicitHeight + 32`); ListView
destroys/recreates off-screen delegates → `contentHeight` recalculated → ScrollBar
ratio changes → jumping.

**Fix:** `cacheBuffer: chatList.height * 3` (keep ~3 screens of delegates alive;
dynamic value to bound RAM on 512 MB board).

### 7.2 Problem B — second question does not auto-scroll

**Symptom:** after scrolling up to read answer 1, sending question 2 did not
scroll to the new content.

**Cause:** auto-scroll only fired when `isNearBottom()` was true.

**Fix:** force `Qt.callLater(chatList.positionViewAtEnd)` inside `send()` —
sending a question means "show me the new stuff".

### 7.3 Problem C — last line hidden behind the input bar

**Fix:** `footer: Item { height: 24 }` spacer + `anchors.bottomMargin: 24` so
`positionViewAtEnd` leaves room below the last bubble.

### 7.4 Problem D — streaming follow stops halfway (the real beast)

**Symptom:** with a very long, tool-heavy answer ("Can you control this
embedded system?" → **967 text_delta events**, many tool turns), the view
followed for a while, then **stopped** — still "Pi agent working..." — and only
after `ready` did the user discover more content below by dragging.

**Diagnosis (recorded full RPC stream):**
- `agent_end` (line 5967) comes **after** the last `text_delta` (line 5962) →
  the ready signal itself is not early.
- The **perceived** "ready too early" was a **UI-stall illusion**: every
  `text_delta` → `partialUpdate` → `chatModel.set()` → full Text re-layout on
  a 396 MHz core → event processing lagged behind, so the visible text hadn't
  caught up when ready appeared.
- The **scroll stall** root cause: throttled updates grow `contentHeight` by
  >50 px at a time; `isNearBottom()` (50 px tolerance) goes false; no more
  `positionViewAtEnd`; `contentY` freezes → **`isNearBottom()` stays false
  forever** (deadlock).

**Fixes (two layers):**
1. **Throttle UI updates** (C++): accumulate deltas, flush via a 100 ms
   single-shot QTimer → 967 sets become ~10 → UI stays responsive (also fixes
   the "ready early" illusion).
2. **Replace the `isNearBottom()` tolerance with a `userScrolling` flag**:
   ```qml
   property bool userScrolling: false
   onDragStarted:  userScrolling = true
   onDragEnded:    userScrolling = false
   onFlickStarted: userScrolling = true
   onFlickEnded:   userScrolling = false

   onContentHeightChanged: {
       if (waiting && !userScrolling)
           Qt.callLater(chatList.positionViewAtEnd)
   }
   onCountChanged: {
       if (!userScrolling)
           Qt.callLater(chatList.positionViewAtEnd)
   }
   ```
   - While streaming: always pin to bottom unless the user is dragging/flicking.
   - **Important:** do **not** use ListView `moving` (it is also true for
     programmatic scrolling → deadlock again); `drag/flick` signals are
     user-only.

## 9. Key Takeaways

1. **The goal is autonomous hardware control, not chat**: the headless RPC +
   extensible-tools design exists so the agent can later drive GPIOs, UART,
   and sensors directly and act on its own decisions.
2. **32-bit ARM + modern Node tooling is viable**: official `linux-armv7l`
   Node prebuilts exist; no compilation needed.
3. **Time sync is mandatory for TLS**: `CERT_NOT_YET_VALID` on any HTTPS client;
   boot-time sync (HTTP `Date:` header) solved it persistently.
4. **pi's process title is `pi`, not `node`** — verify with `ps | grep pi`.
5. **HOME matters**: a QProcess launched from SystemUI inherits `HOME=/`;
   always force `HOME=/root`.
6. **Provider endpoints differ**: OpenCode Zen (`/zen/go/v1`) vs Go-subscription
   endpoint — a custom provider in `models.json` pins the correct one.
7. **RPC mode needs stdin kept open** (EOF kills pi).
8. **Streaming UI must throttle**: per-delta QML `set()` on a slow core stalls
   the UI and *looks* like "ready too early".
9. **`isNearBottom()` tolerance deadlocks under throttled growth** — use a
   user-interaction flag (`drag/flick` signals), never `moving`.
10. **`cacheBuffer` (dynamic, `height*3`) fixes ScrollBar jumping** on
    dynamic-height delegates without OOM.
11. **`footer` spacer** guarantees the last line isn't hidden behind the input bar.
